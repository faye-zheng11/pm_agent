# PRD 写作

## 什么时候使用 / 不使用

### 使用

- 已完成问题定义和范围收敛，需要形成开发可执行的产品需求。
- 需要整理版本 PRD、Feature PRD，或把已确认讨论重构成统一业务事实源。
- 开发要求按 `Epic → Story → FR / NFR → Given-When-Then` 接收需求。

### 不使用

- 还在发散想法、寻找问题或决定做不做：先走产品生命周期前置门禁。
- 只是补一条已确认业务规则：直接更新项目决策记录和 PRD 的业务规则表，不另造平行文档。
- 已有 PRD，只需要拆前端、后端技术任务：交给开发部门的 story 和 task brief 流程。
- 没有 active Bet 的 Pre-PMF 项目：最多形成 `draft / 待验证`，不得写成已批准开发的正式范围。

## 核心目标

PRD 不是越长越专业，也不是所有角色共用的一篇说明书。它应成为团队共同的**业务事实源**，让开发不用发明产品逻辑，就能继续拆前端、后端和 AI 任务。

一份合格 PRD 要同时回答：

1. 为什么做、给谁做、本次要改变什么。
2. 本版本相对现状新增或修改什么，哪些已有能力不重复建设。
3. 用户在什么条件下做什么，系统应产生什么业务结果。
4. 功能要满足哪些质量边界，什么情况算完成。
5. 上线前怎么验，上线后看什么；哪些数字已有依据，哪些只能先建基线。
6. 用户完成动作后，业务状态、其他页面、内容、AI 和存量数据分别发生什么。

## 交付形态与产物

PRD 不止是一段文字，交付时给出可直接用的产物：

- **默认自包含 HTML PRD**：单文件、浏览器直接看，含结构化章节；可导出 **Markdown / PDF / Word**。
- **每个功能配 2–N 条可直接用的编码提示词**：把 FR / 验收翻成开发能贴进 AI 编码器的 prompt，做 PRD→dev 的桥。
- **随 PRD 附**：可证伪 Bet、成功信号与观察窗、未验证标注——让 critic 与开发一眼看清哪些已定、哪些待验。

（渲染由交付后端完成；本 skill 负责结构与内容，产物格式在此声明。）

## Required Project Context

动笔前必须读取：

- `HOME.md`、`PROJECT-CONTEXT.md`、`project.yaml`。
- `memory/canon.md`、`memory/assumptions.md`、`memory/evidence.md`、相关 `memory/decisions/`。
- 当前版本 active Bet；没有 active Bet 时明确文档只能是待验证草稿。
- 上一版本 PRD、现有功能、相关 Feature 和已确认设计，先建立“现状基线”。
- 与本需求相关的真实用户证据、数据口径、聊天样例或用户反馈。
- 用户指定的历史会话、截图、Figma、飞书文档或开发交付格式。

不能只根据当前对话重建需求，也不能把讨论过程中曾出现、后来被推翻的方案写进最终稿。

## 必要输入和信息缺口

最低输入：

- 目标用户和用户任务。
- 当前问题及证据。
- 本版本目标、范围和非目标。
- 当前产品行为与本次变化。
- 已确认业务规则和关键流程。
- 核心业务对象、状态和受影响的产品表面。
- 目标交付读者及其格式要求。

开始前把输入分成三类：

| 类型 | 处理方式 |
| --- | --- |
| 已确认事实 / 决定 | 可以写入正文并注明来源 |
| 有证据的推断 | 标明为方向性判断或待验证假设 |
| 未知 / 冲突 | 进入待确认；会改变范围、流程或数据结构时不得替用户猜 |

信息缺口的处理原则：

- 不影响业务结果的小细节，可以给出保守默认值并明确标注。
- 会改变用户流程、业务状态、内容口径或版本范围的问题，必须确认后再写为需求。
- 阻断开发的未知项标记 `blocked`；非阻断项可以保留 Owner 和截止时间。
- 没有待确认问题时不必为了格式写“本版本无待确认问题”；需要明确交接状态时才写一句。

## 专业模型与术语

### 1. 需求分层

```text
Epic：一组共同服务于同一用户结果的能力
└── Story：一个主要用户触发 + 一个主要用户结果
    ├── FR：系统必须提供的可观察业务行为
    ├── NFR：该能力必须满足的质量属性或跨状态约束
    └── GWT：从外部验证 FR / NFR 是否成立的场景
```

### 2. User Story

统一使用完整语义：

```text
作为 <具体用户或角色>，
为了 <想完成的动作或任务>，
以便于 <获得的结果或价值>。
```

Story 不是章节标题，也不是“建接口”“加埋点”“改数据库”。一个 Story 只承载一个主要触发和主要结果；出现多个结果时继续拆分。

### 3. 功能性需求 FR

FR 描述**系统做什么**，应包含触发、条件、行为和结果中的必要信息，例如：

> `FR-2.1-03`：用户选择暂时离开时，保留当前 Date、对话内容和进度，不生成结束后的 Memory 或承接消息。

FR 必须：

- 可观察、可测试、使用唯一编号。
- 描述业务行为，不指定 API、数据库表、服务拆分或代码方案。
- 把主流程、关键分支和异常结果写清，不依赖开发自行脑补。
- 默认视为本版本必须交付；未来方向、备选方案和“有空再做”不能混入 FR 正文。

### 4. 非功能性需求 NFR

NFR 描述**功能以什么质量成立**，常见类别包括：

- 一致性：多个页面、状态或内容源结果一致。
- 可靠性：切页、重启、重试后不丢失、不重复、可恢复。
- 性能：只写有依据的时间目标；没有依据时先测基线。
- 可观测性：问题能够关联和定位。
- 本地化与可访问性：语言覆盖、长文本、fallback、变量替换。
- AI 质量：事实可追溯、状态不说反、固定样例 Eval 可验证。

不要把 FR 换一种说法重复成 NFR，也不要写“体验流畅”“系统稳定”这种无法验收的空话。

### 5. Given-When-Then 验收

所有验收场景统一使用：

```text
Given <可验证的前置状态>
When <用户动作或系统事件>
Then <可观察结果>
```

每个 Story 至少覆盖主路径；存在关键分支、失败恢复、权限或防重要求时，补对应场景。GWT 验收测试结果，不重复解释需求背景。

### 6. 成功信号

成功信号需要写，但不等于每份 PRD 都必须编一个增长数字。分两层：

| 层级 | 用途 | 写法 |
| --- | --- | --- |
| 上线验收 | 判断功能是否可发布 | 可确定的通过条件，如关键用例通过、内容覆盖率、阻断错误为 0 |
| 上线后观察 | 判断产品方向是否改善 | 指标、口径、观察窗和当前基线；无基线时写“先建基线” |

只有当前 active Bet 已确认目标值和 KILL 条件时，才把产品效果数字写成目标。没有 Bet 或样本依据时，不硬填 A/B 类数字，不用完成率冒充 PMF 信号。

### 7. 背景、摘要和目标

背景按以下因果链写，不写项目历史流水账：

```text
当前情境 → 用户或业务问题 → 证据 → 机制判断 → 为什么现在做 → 本版本回应
```

- **当前情境**：现有流程、能力或市场阶段是什么。
- **问题**：谁在什么场景被卡住，产生什么可观察后果。
- **证据**：行为、访谈或样例支持到哪一步；没有证据的原因解释标为假设。
- **机制判断**：解释为什么会发生，但不得把相关性写成因果。
- **为什么现在**：说明这件事为何进入当前版本，例如阻断核心路径、影响当前 Bet 或扩大测试前必须修复。
- **本版本回应**：只概括变化方向，不在背景里提前展开功能清单。

目标不是“上线某功能”，而是功能带来的结果。至少区分：

| 类型 | 回答的问题 | 例子 |
| --- | --- | --- |
| 用户结果 | 用户完成后获得什么改善 | Date 结束后能自然回到 Chat 继续关系 |
| 业务 / 学习结果 | 本轮要验证或改善什么 | 验证闭环是否带来继续聊天，暂无基线则先建基线 |
| 交付结果 | 本版本必须具备什么能力 | 西语、葡语覆盖已确认的完整语言链路 |

每个目标必须能回溯到一个问题，并能向下映射到 Epic / Story 和观察信号。不要把指标本身当目标，也不要写“优化体验、提升满意度”这种无法判断完成的表达。

摘要使用一段话完成五件事：

```text
为谁做 + 当前什么问题 + 本版改什么 + 预期产生什么结果 + 明确不做什么
```

### 8. 功能完整性模型

写完每个 Story 后，用以下十问检查；不适用项可以跳过，但必须经过判断：

1. **Actor**：谁触发，谁受到结果影响。
2. **入口与触发**：从哪里进入，用户动作或系统事件是什么。
3. **前置条件**：资格、状态、权限、已有数据和阻断条件是什么。
4. **输入与默认值**：用户选择什么，系统沿用什么，缺失时如何处理。
5. **主流程**：正常情况下按什么顺序发生。
6. **分支与限制**：取消、返回、空数据、上限、权限和互斥条件怎么处理。
7. **状态与副作用**：哪些业务对象从什么状态变成什么状态，同时触发或明确不触发什么。
8. **失败与恢复**：失败时用户看到什么，能否重试、继续、回滚，如何避免重复结果。
9. **跨表面影响**：其他页面、内容源、AI / Memory、通知、数据和多语言是否需要同步变化。
10. **存量与完成结果**：历史数据、进行中任务和旧版本用户如何处理，最终什么状态代表真正完成。

状态复杂时，产品必须定义业务状态迁移，而不是只画页面跳转：

| 业务对象 | 当前状态 | 触发 | 下一状态 | 用户可见结果 | 同时发生 / 不发生 |
| --- | --- | --- | --- | --- | --- |

这是业务语义，不是要求产品指定数据库字段。状态名称可以由开发调整，但状态之间的业务区别和结果不能由开发猜。

跨模块功能还要做一次影响面扫描：`UI / 内容源 / AI-Prompt-Memory / 数据埋点 / 运营配置 / 多语言 / 存量兼容`。命中某项就在 PRD 写清业务影响或引用对应规格；没有影响时无需制造章节。

## 决策规则和证据等级

可以引用上游结果中的 `frameworks_used` 作为产品推理背景，但不得把框架名称或框架推导直接写成用户事实、市场事实或已验证结论。PRD 正文只保留会影响范围、状态、验收和待确认项的判断。

真实行为 > 用户访谈 / 原话 > 市场或外部证据 > 专家推断 > Synthetic Persona。

小样本提醒必须紧跟实际证据，写清每个结论的真实分母和限制。不要把多个不同样本统一写成一个 `N=29`，也不要用“方向性证据”掩盖口径不清。

发生冲突时按以下顺序处理：

1. 用户当前明确确认的业务口径或正式决策记录。
2. `canon`、已确认决定和当前版本范围。
3. 已评审 PRD、Figma 和数据定义。
4. 有证据支持但尚未确认的推断。
5. AI、模板或外部评审建议。

低优先级来源不能静默覆盖高优先级来源。不同正式产物互相冲突时，先暴露冲突并确认唯一口径，再继续写作。

其他决策规则：

- 没有 active Bet 的 Pre-PMF 需求只能保持待验证草稿。
- 没有基线、观察窗和 Bet 时，不写产品效果目标值。
- 未确认信息会改变范围、流程或验收时，不自行补全。
- 用户指定了开发交付格式或给出样例时，将其视为交付契约的一部分，但仍检查是否越过产品与技术边界。

## 执行步骤

### Step 1：恢复上下文并建立变化清单

先列出：

| 分类 | 内容 |
| --- | --- |
| 新增 | 本版本第一次提供的能力 |
| 修改 | 对已有行为的变化 |
| 沿用 | 仍然有效但不作为新需求建设的能力 |
| 不做 | 本版本明确排除的内容 |

已有功能不得因为在流程中被提到，就重新包装成新 Story。只有它与新需求存在接口边界时，才作为“沿用规则”引用。

### Step 2：写清背景、目标用户和版本目标

- 按“情境 → 问题 → 证据 → 机制判断 → 为什么现在 → 本版回应”写背景。
- 背景只保留能解释本次取舍的证据，不写完整项目历史或方案讨论过程。
- 目标用户写当前真正服务的人，不把待验证市场写成已确认人群。
- 目标分别检查用户结果、业务 / 学习结果和交付结果；非目标用于守住范围。
- 每个目标向下映射到 Epic / Story 和成功信号，无法映射的目标应删除或补需求。
- 每条数据标明来源、时间、样本和口径；小样本不下显著性或因果结论。

### Step 3：先定义用户旅程和全局业务规则

画出最短主流程，并先写跨 Story 共用规则：

- 入口和前置条件。
- 关键状态及状态变化。
- 权限、限制、计数和结束条件。
- 失败、重试、恢复和 fallback 的业务结果。
- 哪些动作明确“不代表”状态改变。
- 核心业务对象、状态迁移和跨页面副作用。
- 历史数据、进行中流程和旧版本行为如何兼容。

全局规则只写一次，Story 引用它，避免多个章节出现互相冲突的版本。

### Step 4：拆 Epic 和 Story

1. 按用户旅程或用户结果分 Epic，不按前端、后端技术层分 Epic。
2. 每个 Story 只保留一个主要触发和结果。
3. Story 使用“作为 / 为了 / 以便于”完整表达。
4. 埋点、数据库、接口和纯技术任务不单独伪装成用户 Story。
5. 用 Story Map 检查主流程是否连续、范围是否重复或缺口。

### Step 5：为每个 Story 写 FR、NFR 和 GWT

- 先补齐 Story 的入口、前置条件、完成结果、业务对象 / 状态和下游影响。
- 标明 Story 的决策来源以及关联的 Figma、数据或内容规格；找不到来源时先确认它是否真的属于本版本。
- 用功能完整性十问检查主流程、分支、状态、副作用、失败恢复和存量兼容。
- FR 从主流程写到关键分支，编号格式为 `FR-<Story>-<序号>`。
- NFR 只写该 Story 真正需要的质量边界，编号格式为 `NFR-<Story>-<序号>`。
- 某项质量要求由全局 NFR 统一约束时，Story 可以引用全局编号，不要为了填满章节重复造句。
- GWT 覆盖主路径和高风险分支，并能追溯到 FR / NFR。
- 需求用业务语言描述；技术如何实现由开发决定。

### Step 6：处理页面、文案、内容源和多语言

- PRD 写页面的业务目的、入口、状态和操作结果。
- 精确 UI 文案可以落在 Figma / Frontend Spec，但会改变业务含义、用户承诺或选择结果的文案语义必须在 PRD 中明确。
- “覆盖全部界面”必须转成可核对的清单或清单生成规则，不能作为一句模糊需求交付。
- 多语言至少检查：设置入口、所有 UI 状态、用户可见内容源、AI/角色回复、locale 保存与生效、历史内容、fallback、长文本、变量、缓存与缺失观测。

### Step 7：处理 AI-native 状态连续性和 Eval

涉及 AI 对话、关系或生成内容时，对每个关键动作回答：

1. 用户刚做了什么。
2. 系统承认并保存了什么状态。
3. UI 应显示什么。
4. 模型 / prompt 应知道什么、不应知道什么。
5. 哪些事实进入短期或长期 Memory。
6. 下一次互动应如何受影响。
7. 失败或恢复时如何避免状态说反、重复推进或捏造事实。

AI 输出质量不能只写“更自然”。必须给期望行为、禁止行为和覆盖关键情境的 Eval 样例；prompt 不能代替未定义的业务状态。

### Step 8：写上线验收、观察信号和数据要求

- 上线验收聚合各 Story 的关键 FR、NFR 和 GWT。
- 上线后观察写指标、口径、观察窗和当前基线。
- 没有基线时写“上线后先建基线”，后续由对应 Bet 确定目标值和停止条件。
- 埋点放在独立数据章节，不作为 Story；优先复用现有事件，只补无法回答问题的缺口。
- 生成类能力同时定义离线 Eval 和线上行为信号。

### Step 9：只保留有用的附加章节

以下章节按需出现，不强制凑齐：

- UI / Figma 影响。
- 数据与 Eval。
- 依赖和风险。
- 待确认问题。
- 关联资料。

依赖、风险或待确认会阻断交付时必须写；为空且不影响读者时可以省略。PRD 的专业度来自定义准确，不来自章节数量。

### Step 10：做交付前回验

至少完成三次检查：

1. **业务一致性**：正文是否只保留最终决定，是否残留被推翻方案或把 1.0 能力写成 2.0 新需求。
2. **开发可执行性**：开发能否逐个 Story 识别 FR、NFR、GWT，而不需要猜业务结果。
3. **跨产物一致性**：PRD、Figma、Feature、数据方案和飞书版本的命名、流程和状态是否一致。

写入飞书或其他共享文档后，应回读目录和关键章节，确认编号、内容和版本没有错位。

## 产品与开发的边界

产品负责：

- 用户目标、版本范围、业务对象、业务状态、规则和预期结果。
- 页面需要表达的业务状态和关键文案语义。
- 功能验收、体验验收、数据问题和 AI Eval 目标。

产品不负责：

- API 名称、请求字段、数据库表、服务拆分和代码结构。
- 替前端确定组件实现，或替后端确定存储和并发方案。
- 把未经确认的技术限制倒写成业务规则。

复杂项目可由开发基于同一 PRD 继续生成：

- Frontend Story：页面、组件状态、交互、文案、加载 / 空 / 错误态。
- Backend Story：业务能力、状态流转、边界、副作用和系统验收。
- AI Task Brief：当前任务、必要上下文、业务规则、好坏样例和验收。

这些是对 PRD 的角色化翻译，不能重新定义产品价值或业务规则。

## 输出契约

默认使用以下最小结构，按复杂度增删，不强制写空章节：

1. 文档元信息：状态、版本、Owner、日期、关联 Bet / Feature。
2. 一段话摘要。
3. 背景与证据。
4. 目标用户、版本目标、非目标。
5. 全局业务规则和主流程。
6. 核心对象、状态迁移和影响面（复杂需求按需）。
7. Story Map。
8. `Epic → Story → 场景定义 → FR / NFR → GWT`。
9. 上线验收与上线后观察。
10. 数据、Eval、阻断项和关联资料（按需）。

写入位置：

- 版本级 PRD：`projects/<项目>/versions/<版本>/release/PRD.md`。
- Feature 级需求：`projects/<项目>/versions/<版本>/features/<slug>/`。
- 已确认长期事实、假设、证据和决定分别回写项目 `memory/` 对应位置。
- 改动 `feature.yaml` 阶段状态后运行 `python3 scripts/gen_status.py`，不手改 `STATUS.md`。

Readiness：

- `draft`：结构已形成，但仍有非阻断未知项或没有 active Bet。
- `review`：业务规则完整，等待跨部门评审。
- `ready`：阻断问题已关闭，设计 / 开发 / 数据可继续拆解。
- `blocked`：存在会改变范围、流程或验收的关键未知项。

## 失败模式、反例和安全边界

- **一份万能长文档**：所有页面、技术、文案和埋点混在一起，读者找不到自己的入口。
- **极简到无法开发**：只有“问题是什么、想达到什么体感”，没有 Story、FR、NFR 和验收。
- **企业模板表演**：为了显得专业，强行补“本版本无待确认问题”、空风险表和无依据数字。
- **把已有功能重新算需求**：流程中提到 24 小时结束或拒绝邀请，就误写成本版新 Story。
- **让开发猜结果**：写“优化退出体验”，却不说明暂时离开和真正结束分别发生什么。
- **把实现当需求**：产品直接指定字段、表结构或接口，而业务状态仍然没定义。
- **FR / NFR 混用**：把“提供重试按钮”和“体验稳定”分别写成 FR / NFR，却都无法说明失败后的业务结果。
- **把埋点当 Story**：数据采集脱离产品目标，Story Map 被技术事项打断。
- **成功信号造数**：没有基线和 Bet 仍填转化率目标，或用上线完成证明 PMF。
- **小样本过度结论**：把相关性写成因果，把不同口径合并成统一 N。
- **AI 状态断片**：只写页面跳转，不定义角色应知事实、Memory 和下一次互动变化。
- **多语言一句话包打天下**：只写“新增西语和葡语”，漏掉设置、内容源、回复语言、fallback 和长文本。

安全边界：

- Canon、active Bet、版本范围和重要业务决定必须由 PM 明确确认后再固化。
- 真实用户聊天样例进入 PRD 时应最小化引用并去除可识别信息。
- 外部 AI、模板或历史文档只提供建议，不能自动变成项目事实。
- 覆盖共享文档前确认目标和权限；写入后回读验证，不把写入成功等同于内容正确。

## 质量 Rubric

交付前逐项检查：

- [ ] 当前版本的新增、修改、沿用和不做是否分清。
- [ ] 背景证据是否能解释本次取舍，样本和限制是否准确。
- [ ] 背景是否区分已确认问题与原因假设，并讲清为什么现在做。
- [ ] 目标用户是否真实，未把待验证市场写成已确认分层。
- [ ] 每个目标是否描述结果，并能映射到问题、Story 和观察信号。
- [ ] 每个 Epic 是否服务一个用户结果。
- [ ] 每个 Story 是否有完整“作为 / 为了 / 以便于”。
- [ ] 每个 Story 是否讲清入口、前置条件、完成结果、状态和下游影响。
- [ ] 每个 Story 是否有编号清楚、可测试且不指定技术实现的 FR。
- [ ] NFR 是否是具体质量边界，而非重复 FR 或空话。
- [ ] 所有验收是否使用 GWT，且覆盖关键分支和失败恢复。
- [ ] 业务规则、状态和页面结果是否不存在互相冲突。
- [ ] 是否检查跨页面、内容源、AI / Memory、数据、多语言和存量兼容影响。
- [ ] 文案、Figma、数据和 AI 规格是否与 PRD 共用同一业务事实。
- [ ] 埋点是否放在数据章节，并能回答明确分析问题。
- [ ] 成功信号是否区分上线验收和产品观察，没有编造目标数字。
- [ ] AI 功能是否定义状态连续性、禁止行为和 Eval。
- [ ] 待确认问题是否真的可见；没有则不制造形式性内容。
- [ ] 开发能否继续拆前后端 Story，而不用重新定义业务。

所有适用检查项通过且不存在阻断问题，才可标记 `ready`。

## Golden Example

```markdown
### Epic 2：管理 Date 的暂时离开和结束

目标：让用户明确区分离开页面与结束当前 Date。

#### Story 2.1：暂时离开 Date

> 作为正在 Date 中的用户，
> 为了先去处理其他事情，
> 以便于稍后回到同一次 Date 继续互动。

##### 功能性需求 FR

- `FR-2.1-01`：用户选择暂时离开后，返回 Chat 并保留当前 Date、消息和进度。
- `FR-2.1-02`：暂时离开不生成 Memory 或 Date 结束后的承接消息。

##### 非功能性需求 NFR

- `NFR-2.1-01`：App 重启后仍能恢复同一次 Date，且消息顺序不变。
- `NFR-2.1-02`：重复点击继续入口不得创建新的 Date。

##### 验收

- Given 用户在 Date 中选择暂时离开，When 从 Chat 点击继续，Then 返回同一次 Date 并看到原消息和进度。
- Given 用户只是切换页面或将 App 放到后台，When 再次进入，Then Date 仍在进行且未生成结束内容。
```

这个例子写清了用户价值、业务结果、可靠性边界和验证方式，但没有替开发指定接口或存储方案。

## Anti-example

```markdown
### Story：优化 Date 退出

- 增加退出弹窗。
- 后端新增 paused 字段并写数据库。
- 体验要流畅稳定。
- 埋点退出按钮。
- 成功指标提升 20%。
```

问题：没有用户价值和状态结果；擅自指定实现；NFR 不可验证；埋点没有分析目的；成功数字无基线；开发仍需猜“退出后 Date、Memory 和 Chat 分别发生什么”。
