# PM 工作台界面质量基线

这份基线用于 `user-experience-reviewer` 评审 PM 工作台、产品方案、PRD 和 HTML Demo 的界面与交互。它吸收 UI Skills 的界面工程原则和 Behance SaaS / 产品管理后台案例中可复用的结构经验，但不复制任何具体作品的视觉资产。

## 1. 先解决一个任务

- 每个页面先回答：用户现在要完成什么、下一步是什么。
- 一屏只保留一个主动作，最多两个次动作；其他动作进入清晰的“更多”或详情。
- 导航按用户工作语言命名，不按内部模块、服务或技术名命名。
- 对 PM 工作台，首页优先显示当前项目、阶段、当前任务、阻塞和下一步，不优先展示能力数量或系统状态。

## 2. 用渐进展开承载复杂度

- 初始决策点尽量不超过四个可见选项；多个模式用菜单、分组或后续步骤展开。
- 不重复展示同一份项目上下文；项目名、阶段和版本在固定上下文区出现一次，正文只补充变化。
- 原始 JSON、Trace、工具细节和低频配置默认收起，但必须有明确的展开入口。
- 空状态要告诉用户下一步能做什么；加载状态要说明正在做什么；失败状态要说明缺什么和如何恢复。

## 3. 让结构表达真实关系

- 通过对齐、留白和顺序表达层级，分隔线和卡片只在确实需要时使用。
- 工作流是有真实顺序的内容才使用编号和阶段轨道；装饰性编号不使用。
- 结果页优先呈现一句话判断、关键 Finding、下一步和限制，再提供完整原始结果。
- Agent 页必须同时显示：它负责什么、当前项目上下文、输入、运行状态、产物和失败边界。

## 4. 视觉与文字

- 视觉风格必须来自产品任务。PM 工作台应有“研究与判断工具”的秩序感，不使用营销首页、装饰性渐变、无意义插画或泛化 AI 光效。
- 颜色用于表达阶段、状态和操作反馈，不能让每个区块都有独立强调色。
- 一套字体和有限的字号层级足够；长标题、长项目名和多语言必须自然换行，不能依赖固定宽度截断关键信息。
- 控件文案使用用户能理解的动作，例如“开始评审”“确认项目上下文”“继续运行”，不使用“提交”“执行节点”等内部词。

## 5. 交互、无障碍和响应式

- 所有可操作控件有可见焦点、明确标签和至少 44px 的触达区域；状态不能只靠颜色表达。
- 手机视口下，导航、项目切换、主动作和结果必须可达；不能出现横向溢出、遮挡或底部按钮被键盘覆盖。
- 动画只用于反馈、状态变化和空间关系；尊重 `prefers-reduced-motion`，不使用无目的持续动效。
- 评审必须覆盖首屏、空、加载、错误、成功、禁用、长文本、窄屏和退出路径。

## 6. 评审输出

每条 UI Finding 需要说明：受影响的用户和任务阶段、实际可观察证据、问题、影响、修改建议、验收条件和是否需要真人验证。只看到代码但没有运行证据时，标记“未核验”，不能假装完成视觉评审。

推荐优先级：

1. 阻断任务、误导用户、造成数据丢失或不可访问的 HIGH。
2. 明显增加认知负担、导致流失或影响关键决定的 MEDIUM。
3. 只影响精致度且不阻断任务的 LOW。

## 7. 明确不吸收的内容

- 不把 Behance 的展示型视觉、营销式 Hero、装饰性动效搬进业务工作台。
- 不为了“看起来高级”增加新的 Agent、导航入口、图表或复杂组件。
- 不用单纯的审美评分替代可完成任务、可理解状态和可验证结果。
