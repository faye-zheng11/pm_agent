# PM Framework Catalog

> 这是四个 PM Agent 共用的方法目录，不是第五个 Agent，也不是证据库。
> 框架帮助 Agent 提问、拆解和组织判断；真实用户、项目文件、公开来源和数据 Agent 才能作为证据。

## 使用总则

1. 先判断任务属于机会发现、产品塑形、体验走查还是独立评审，再选框架。
2. 一次任务最多使用两个框架。框架不能为了“看起来专业”而强行套用。
3. 每个被使用的框架必须写入结果 `frameworks_used`，包含 `id`、`purpose`、`input_basis`、`output_used` 和 `evidence_boundary`。
4. 没有合适框架时返回 `frameworks_used: []`，并在 `output_used` 不适用时通过普通结论说明原因；不要凭空制造框架结论。
5. 框架输出只能是分析结构、问题清单或候选方向，不得升级为用户需求、市场事实、PMF 或 Pass/Block 证据。
6. 框架中的示例、数字、行业说法都不是当前项目事实；需要事实时必须再走 Web、项目资料或真实数据 Agent。

## 框架条目

### `jtbd` · 用户要完成什么任务

- **适用**：想法仍停留在功能名，或需要从“用户想要 X”改写成情境、动机和结果。
- **输入**：目标用户线索、触发情境、当前替代、期望结果。
- **提问**：用户在什么时候被触发？现在用什么完成？为什么继续忍受它？什么结果算完成？
- **输出**：用户任务、情境、功能性/情绪性/社会性结果，以及替代方案。
- **不能证明**：用户规模、普遍需求、愿意付费或产品已经成立。

### `pain-solution-matrix` · 痛点与解决方案矩阵

- **适用**：筛选机会、判断是否过度设计，或比较“痛点强度”和“现有解决完整度”。
- **输入**：可观察用户行为、困扰、现有替代和拟议方案。
- **输出**：高痛点/低解决、高痛点/高解决、低痛点/低解决、低痛点/高解决四类；指出最值得验证的象限。
- **不能证明**：矩阵位置本身不是市场规模，也不能替代用户证据和实验。

### `user-journey-map` · 用户旅程地图

- **适用**：检查完整使用路径、跨触点摩擦、前后状态和流失点。
- **输入**：目标用户、触发情境、进入/理解/尝试/反馈/复访/退出路径。
- **输出**：阶段、用户目标、触点、情绪或阻力、机会和验证问题。
- **不能证明**：模拟旅程不能当作真实用户研究；没有材料时必须标为推断。

### `mental-models` · 心智模型

- **适用**：用户以为产品会怎样工作，但界面、文案或系统状态实际表达不同。
- **输入**：用户预期、产品概念模型、界面/反馈/错误状态。
- **输出**：预期与实际的落差、误解风险、需要改写或验证的交互。
- **不能证明**：不能单凭框架判断用户一定会喜欢或一定会流失。

### `elevator-pitch` · 一句话产品判断

- **适用**：方案太复杂、团队各说各话，需要压缩成目标用户、问题、机制和差异。
- **输入**：目标用户、主要问题、核心机制、价值和差异。
- **输出**：一句话产品判断，以及仍然缺失的关键条件。
- **不能证明**：表达清楚不等于需求成立，不得把 Pitch 当作立项依据。

### `wardley-mapping` · 价值链与成熟度

- **适用**：独立评审产品战略、平台依赖、自研/购买/外包和技术投入时机。
- **输入**：用户结果、能力链、依赖、当前成熟度和变化方向。
- **输出**：价值链、关键依赖、成熟度假设、可逆的 build/buy/partner 选项。
- **不能证明**：没有真实业务和技术资料时，只能作为战略假设，不能直接决定预算。

## Agent 路由

| Agent | 优先框架 | 使用边界 |
|---|---|---|
| `opportunity-researcher` | `jtbd`, `pain-solution-matrix` | 只用于把外部信号转成用户行为和机会筛选，不用于替代来源核验 |
| `product-shaper` | `jtbd`, `elevator-pitch`, `pain-solution-matrix` | 用于问题定义和方案收敛，不能跳过 Bet 或直接把结果写成正式 PRD |
| `user-experience-reviewer` | `user-journey-map`, `mental-models` | 用于走查和发现误解，模拟结论必须和真人证据分开 |
| `independent-critic` | `pain-solution-matrix`, `wardley-mapping` | 用于找反例和战略风险，不替 PM 决定预算，不自动改变 Pass/Conditional/Block |

## 选择规则

- 有明确用户情境但没有清晰任务：优先 `jtbd`。
- 有很多“看起来很火”的信号但不知道值不值得做：优先 `pain-solution-matrix`，先找行为和替代。
- 产品方案已经写出但流程可能断裂：优先 `user-journey-map`。
- 用户可能误解产品承诺、身份、状态或 AI 角色：优先 `mental-models`。
- 团队无法用一句话说明做什么：优先 `elevator-pitch`，但仍要列证据缺口。
- 争论自研、外部能力、平台依赖或投入时机：优先 `wardley-mapping`，并标注其战略假设性质。
